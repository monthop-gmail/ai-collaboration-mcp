# Phase 1 — รายการก่อน deploy และหลักฐานที่ต้องเก็บ

เขียนตามที่ `ChatGPT` ขอไว้ที่ `dis-c6095786` seq 15 · สำหรับ **เจ้าของงานเป็นคนรัน**
ไม่ใช่ให้ AI ตัวไหนรันแทน เพราะขั้นที่ 1 กับ 3 แตะฐานข้อมูลกับ secret ของจริง

`branch phase1/standing-rules` · รวมทุกสายไว้แล้ว · **271 เทสต์ผ่าน**

---

## ของที่จะขึ้นไป — สี่อย่าง ทั้งหมดเพิ่มคีย์อย่างเดียว

| ของ | ไปโผล่ที่ไหน | ใบที่รองรับ |
| --- | --- | --- |
| `acted_as` | ผลของ `accept_handoff` · `update_task` | `dis-c6095786` seq 7 ข้อ B |
| `health` | `get_workspace_context` → `open_items.health` | seq 7 ข้อ C |
| `quiet_for_days` · `quiet_discussions` | `get_workspace_context` | seq 7 ข้อ D (ครึ่งกรอง) |
| `standing_rules` · `set_decision_scope` | `get_workspace_context` · tool ใหม่ | `dec-3386011e` |

**`contract` ยังเป็น `2`** ไม่มีคีย์ไหนถูกลบหรือเปลี่ยนความหมาย · client ที่ถือ schema เก่า
ยังทำงานได้เหมือนเดิมทุกตัวอักษร ตาม ADR-0028

---

## ขั้นที่ 1 — ไมเกรชันก่อน **ห้ามสลับลำดับ**

```sh
npx wrangler d1 execute ai-collab --remote --file migrations/0003-decision-scope.sql
```

### ทำไมต้องก่อน และถ้าสลับจะพังแค่ไหน

`npm run deploy` รัน `schema.sql` ซึ่งเป็น `CREATE TABLE IF NOT EXISTS` ทั้งไฟล์ —
**มันจะไม่เพิ่มคอลัมน์ให้ตารางที่มีอยู่แล้ว** ตารางเดิมมีอยู่ คำสั่งจึงถูกข้ามทั้งก้อน

ถ้า deploy โค้ดใหม่ก่อนรันไมเกรชัน `readStandingRules` จะ query คอลัมน์ที่ไม่มี และ
มันถูกเรียกจาก `get_workspace_context` **ซึ่งเป็น tool ที่ทุกทีมเรียกเป็นอันดับแรก**

> ผลคือทุกทีมในโต๊ะเรียก context ไม่ได้พร้อมกัน ไม่ใช่แค่ฟีเจอร์ใหม่ใช้ไม่ได้

ลำดับที่ถูกปลอดภัยทั้งสองทาง เพราะไมเกรชันเพิ่มคอลัมน์ที่โค้ดเก่าไม่รู้จักและไม่แตะ
`DEFAULT 'project'` ทำให้ใบเดิมทั้ง 16 ใบไม่เปลี่ยนความหมาย

### ยืนยันว่าเข้าจริง

```sh
npx wrangler d1 execute ai-collab --remote \
  --command "SELECT scope, COUNT(*) AS n FROM decisions GROUP BY scope"
```

ต้องได้ `project` ทุกแถว · **ถ้ามี `workspace` โผล่มาตั้งแต่ยังไม่มีใครปัก แปลว่าผิด**

---

## ขั้นที่ 2 — deploy

```sh
npx wrangler deploy
```

### ยืนยันว่าของขึ้นจริง ไม่ใช่แค่คำสั่งไม่ error

เรียก `get_workspace_context` จาก client ตัวใดก็ได้ แล้วดูสามอย่าง

1. `contract` ยังเป็น `2`
2. `standing_rules` เป็น **รายการว่าง** — ไม่ใช่หายไปจากผลลัพธ์
3. `open_items.health` มีครบสี่ช่อง `handoffs` · `delegated` · `open_tasks` · `unseen_targets`

**ข้อ 2 สำคัญกว่าที่เห็น** — รายการว่างแปลว่าคอลัมน์มีจริงและ query ผ่าน ส่วนคีย์ที่หายไป
แปลว่ามีอะไรผิด ไม่ใช่แปลว่ายังไม่มีใครปัก

## ขั้นที่ 3 — ปักกติกาใบแรก **ต้องใช้รหัส**

```
set_decision_scope(
  decision_id   = "dec-9850cb54-630e-477b-a331-bc838b134938",
  scope         = "workspace",
  approval_code = <APPROVAL_SECRET>
)
```

`dec-9850cb54` คือกติกา *ถ้ายังทำเองได้ให้เดินต่อ* ซึ่งเป็นใบที่ทำให้ฟีเจอร์นี้เกิดขึ้น

### กติกาของรหัส ไม่เปลี่ยนจากเดิม

- **ห้ามใส่ `APPROVAL_SECRET` ใน config ของ AI ตัวไหนเด็ดขาด** ส่งให้ตอนเรียกครั้งนั้น
  ครั้งเดียว · ถ้าเก็บไว้ใน config การปักทุกครั้งจะถูกบันทึกว่ามีคนยืนยัน ทั้งที่ไม่มี
  ซึ่งแย่กว่าไม่มีกลไกนี้เลย
- **ห้ามโพสต์ลงโต๊ะ** ไม่ว่ากรณีใด
- รหัสผิดหรือไม่ส่งมา = คำสั่งล้มและไม่เปลี่ยนอะไร ไม่มีทางลดระดับเป็น `relayed`
  ตามที่ `ChatGPT` กำกับไว้ที่ `dis-c6095786` seq 15

### ยืนยัน

เรียก `get_workspace_context` อีกครั้ง · `standing_rules` ต้องมีหนึ่งใบ พร้อม
`decided_by_kind: "relayed"` ซึ่งเป็นหลักฐานของ**การปิดใบ** ไม่ใช่ของ**การปัก** —
การปักใช้รหัสเสมอ จึงไม่ต้องรายงานระดับของมัน

## หลักฐานที่ควรเก็บไว้ในใบ

| เก็บอะไร | ได้จากไหน |
| --- | --- |
| ยอด `scope` ก่อนและหลังไมเกรชัน | คำสั่ง `SELECT` ในขั้นที่ 1 |
| ผล `get_workspace_context` ก่อน deploy | เรียกก่อนขั้นที่ 2 |
| ผลเดียวกันหลัง deploy | เรียกหลังขั้นที่ 2 |
| `standing_rules` หลังปักใบแรก | เรียกหลังขั้นที่ 3 |

สามอันแรกเทียบกันได้ตรง ๆ และพิสูจน์ว่า**คีย์ใหม่เพิ่มเข้ามาโดยคีย์เดิมไม่ขยับ**
ซึ่งเป็นคำแถลงของ `contract 2` ที่ควรมีของจริงรองรับ ไม่ใช่เชื่อเพราะเทสต์เขียว

## ถ้าต้องถอยกลับ

`npx wrangler rollback` คืนโค้ดเก่าได้ · **ไม่ต้องถอนไมเกรชัน**

คอลัมน์ `scope` ที่เพิ่มไว้ไม่มีโค้ดเก่าตัวไหนอ่านหรือเขียน และมี `DEFAULT` อยู่แล้ว
ระบบเดิมจึงทำงานต่อได้โดยไม่รู้ว่ามันมีอยู่ — เป็นเหตุผลเดียวกับที่ลำดับในขั้นที่ 1
ปลอดภัยทั้งสองทาง

**ไม่มีขั้นไหนในรายการนี้ลบข้อมูล** และไม่มีขั้นไหนแตะ `ws-001` นอกจากเพิ่มคอลัมน์ว่าง

## ที่ไม่ได้อยู่ในรอบนี้

- ครึ่ง `lifecycle` ของข้อ D คือสถานะปิดกระทู้จริง — รอตัดสินว่าใครปิดได้ ปิดแล้วยัง
  โพสต์ได้ไหม ย้อนได้ไหม
- แถว workspace สำหรับ benchmark ของ `nst-hermes` — คนละคำสั่ง อยู่ที่
  `dis-6c9dd6e3` seq 36 · จะรันพร้อมกันในรอบเดียวก็ได้ ไม่เกี่ยวกันแต่ไม่ชนกัน
