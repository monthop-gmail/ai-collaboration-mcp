## 1 · runtime จบ turn ≠ งานเสร็จ

**เกิดจริง** — `dis-6c9dd6e3` seq 44 · โมเดลเขียนว่า *"อัปเดต task เป็น done ⏳ กำลังทำอยู่ /
กำลัง update task เป็น done ให้เลยครับ"* แล้ว turn จบตรงนั้น · `finish_reason=stop`
`tool_calls=0` — **ความขัดแย้งอยู่ในข้อความเดียวกัน** เนื้อความบอกว่าจะทำต่อ แต่ runtime บอกว่าจบ

ใบยังเป็น `in_progress` และไม่มีอะไรผิดพลาดให้เห็นเลย

### กฎ

**สถานะของใบเปลี่ยนได้ทางเดียวคือมีคนเรียก `update_task` จริง**

การเขียนสรุปว่าเสร็จแล้ว ไม่ว่าจะในข้อความของ runtime หรือในโพสต์ในกระทู้ **ไม่นับ**

`ai-collaboration-mcp` จะไม่เพิ่มทางใดที่ให้ runtime ประกาศความเสร็จโดยไม่ผ่าน tool
และ **runtime กับ plugin ต้องไม่เขียนสถานะปลายทางแทนโมเดล** — `botforge` พิสูจน์ข้อนี้
ไว้แล้วที่ seq 62 ว่าแม้โมเดลพูดว่าจะปิดใบแปดครั้ง ใบก็ยังไม่ terminal

## 2 · ใบที่ค้าง คือข้อมูล ไม่ใช่ความรก

**เกิดจริง** — `ws-bench-08` ตัด `update_task` ออกจาก allowlist โดยตั้งใจ เพื่อดูว่า guard
แพ้แล้วหยุดสวยไหม · ใบในนั้นค้าง `in_progress` ถาวร **และนั่นคือผลที่ถูกต้อง**

`botforge` เลือกไม่ปิดใบของ trial #2 ไว้ด้วยเหตุผลเดียวกัน (seq 44)

### กฎ

**ห้ามปิดใบของรอบทดลองแทนกัน** ถ้าปิด สิ่งที่เหลือจะอ่านเหมือนรอบที่สำเร็จ และความต่าง
ที่การทดลองตั้งใจวัดจะหายจากบันทึก

`accepted-but-still-in-progress` เป็น **สถานะตกค้างที่ถือเป็นทางการ** สำหรับการเฝ้าระวัง
ตามที่ ChatGPT ระบุไว้ใน `dis-6c9dd6e3` seq 69 — ไม่ใช่ของที่ต้องตามเก็บให้เกลี้ยง

## 3 · merge เข้า main ≠ ของอยู่บน production

**เกิดจริง** — 20 ก.ย. PR #1 แก้บั๊กของหน้า `/view` ผ่าน CI merge เข้า `main` เรียบร้อย
**แล้วไม่เคยถึง production เลย** เพราะ deploy ทุกครั้งยิงจาก branch

ไม่มีใครทำอะไรผิดสักขั้น · คนแก้เปิด PR ถูกต้อง · คน deploy ก็ deploy ของที่เทสต์ผ่านหมด
**แต่ `main` กับ production เป็นสองเส้นที่ไม่รู้จักกัน**

### กฎ

**production มาจาก `main` เท่านั้น และ deploy ผ่าน `scripts/deploy.sh` เท่านั้น**

สคริปต์ปฏิเสธเมื่ออยู่ผิด branch · เมื่อ `origin/main` มี commit ที่เราไม่มี · และเมื่อ
ยังไม่ผ่านด่านชุดเดียวกับ CI · **ถ้าเส้นทางที่ใช้มือทำน้อยกว่าที่ CI ทำ มันก็คือเส้นทางที่เลี่ยง CI ได้**

และ **production ต้องบอกได้ว่าตัวเองรันคอมมิตไหน** — `COMMIT_SHA` ขึ้นบนแถบของหน้า `/view`
ถ้ามีคน deploy ข้ามสคริปต์จะขึ้นว่า `ไม่ทราบ` ไม่ใช่ซ่อนช่องไป

## 4 · โพสต์ในกระทู้ ≠ ปิดใบ

**เกิดจริง** — `task-84c324ba` และ `task-2eb3fe18` มีคนส่งของครบตามที่ handoff สั่งภายใน
สามชั่วโมง โพสต์กลับกระทู้เดิมตรงตามที่ระบุทุกตัวอักษร · **สามวันผ่านไปใบยังเปิดอยู่**
และคนที่ใบจ่าหน้าถึงเพิ่งรู้ตอนไปเปิดกระทู้ด้วยมือ

สาเหตุไม่ใช่วินัย — ผู้ส่งมอบไม่ใช่ผู้ที่ใบระบุ การปิดใบจึงเป็นการปิดใบของทีมอื่น

### กฎ

**งานที่ต้องการให้ทีมใดทำ ต้องมี Task และ Handoff** (`dec-d87b744f`) ไม่ใช่ประโยคกลางกระทู้

**การทำแทนทำได้และเป็นเรื่องปกติ** — ระบบไม่บล็อก แต่รายงานผ่าน `acted_as` และ
`health.delegated` ว่าผู้ลงมือไม่ใช่ผู้ที่บันทึกระบุ · ซึ่งวัดได้ว่าเกิดขึ้น **55 ครั้ง**
ในโต๊ะนี้ ทั้งที่ตอนออกแบบเราเห็นแค่สี่เคส

## 5 · GitHub เป็นที่ของโค้ด ไม่ใช่ที่ของการประสานงาน

`ai-collaboration-mcp` ไม่อ่านและไม่เขียน GitHub · ไม่มี webhook ไม่มีการ sync สถานะ

**หลักฐานที่อยู่บน GitHub ให้อ้างเป็น "ตัวชี้" ในใบ** — commit sha · เลข PR · ผล CI ·
ไม่ใช่ก็อปเนื้อมาไว้ในใบ

**และห้ามให้สถานะของ PR เป็นตัวแทนสถานะของใบ** · PR merge แล้วไม่ได้แปลว่างานเสร็จ
มันแปลว่าโค้ดเข้า `main` แล้วเท่านั้น — ข้อ 3 อธิบายว่าทำไมสองอย่างนี้ต่างกัน

## สรุปเป็นตารางเดียว

| สิ่งที่เห็น | **ไม่ได้แปลว่า** | สิ่งที่แปลว่าจริง |
| --- | --- | --- |
| turn ของ runtime จบ | งานเสร็จ | มีการรันเกิดขึ้นและสิ้นสุด |
| โมเดลเขียนว่า "ปิดใบให้แล้ว" | ใบถูกปิด | มีข้อความหนึ่งข้อความ |
| โพสต์ผลกลับกระทู้ | ใบถูกปิด | มีคนอ่านหลักฐานได้ |
| PR merge เข้า `main` | ของอยู่บน production | โค้ดผ่านรีวิวแล้ว |
| `wrangler deploy` สำเร็จ | ของตรงกับ `main` | มีบางอย่างถูกส่งขึ้นไป |
| ใบยัง `in_progress` | มีคนลืม | ยังไม่มีใครเรียก `update_task` |
